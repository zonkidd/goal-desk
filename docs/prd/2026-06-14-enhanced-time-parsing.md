# 增强版自然语言时间解析 PRD

**Label**: ready-for-agent

**文档版本**: v1.0  
**创建日期**: 2026-06-14  
**状态**: 待实现

---

## Problem Statement

当前 Quick Capture 的自然语言时间解析能力非常有限，只支持 4 种硬编码的时间表达式（"明天下午三点"、"明天三点"、"明天"、"今晚"）。这导致用户在快速创建待办事项时，仍然需要手动设置时间属性，违背了"无摩擦捕获"的设计理念。

具体痛点：
1. **表达式覆盖不足**：无法识别"后天"、"3天后"、"下周五"、"本周末"等常用表达
2. **时间点识别单一**：只能识别"下午三点"，无法识别"15:30"、"早上9点"、"晚上8点"等
3. **缺少截止时间支持**：无法区分"明天3点开会"（开始时间）和"明天3点前提交"（截止时间）
4. **解析不够智能**：输入"3点开会"会被误判为凌晨3点，而非下午3点
5. **频繁解析失败**：用户反馈"经常解析不出来"，导致仍需手动设置时间

---

## Solution

构建一个覆盖 30+ 常用时间表达式的增强版自然语言解析引擎，支持相对日期、绝对日期、时间段、时间点等多种表达方式，并能够区分开始时间（`planned_start_at`）和截止时间（`due_at`）。

核心能力：
- **相对日期**：今天/明天/后天/N天后/下周一/本周五
- **时间点**：HH:MM 格式、下午3点、早上9点、晚上8点
- **智能补全**：只有日期时默认补充 9:00；只有时间时默认今天；单独"3点"自动判断为下午
- **截止时间识别**：检测"前"、"之前"、"截止"等关键词，将时间分配到 `due_at` 字段
- **保持简单**：轻量级实现，无需外部 NLP 库，零依赖

## User Stories

1. 作为工作用户，我希望输入"3天后提交报告"就能自动设置为3天后的上午9点，这样我就不用打开日历手动选择日期
2. 作为会议密集型用户，我希望输入"下周五下午2点开会"能准确识别日期和时间，这样我就能快速记录会议安排
3. 作为习惯用24小时制的用户，我希望输入"明天15:30评审"能识别15:30这个时间格式，而不是只支持中文表达
4. 作为需要管理截止日期的用户，我希望输入"周五之前完成方案"能识别为截止时间而非开始时间，这样系统就能正确提醒我
5. 作为晚归的用户，我希望输入"今晚8点健身"能识别为晚上8点而非早上8点，避免时间歧义
6. 作为早起的用户，我希望输入"明早7点晨跑"能识别为早上7点，支持早起时间段
7. 作为习惯说"后天"的用户，我希望输入"后天下午开会"能正确解析为2天后，扩展相对日期表达
8. 作为输入"3点开会"的用户，我希望系统智能判断为下午3点而非凌晨3点，避免反直觉的解析结果
9. 作为重度用户，我希望输入"下个月15号提交"也能被识别（未来扩展），逐步覆盖更多场景
10. 作为浏览器预览用户，我希望在非 Tauri 环境下也能体验基本的时间解析能力，保持功能一致性
11. 作为关注数据准确性的用户，我希望任务的 `planned_start_at` 和 `due_at` 字段被正确填充，而不是全部挤在 `due_at` 里
12. 作为需要在 Timeline 上看到任务的用户，我希望有开始时间的任务自动显示在今日时间线上，而不是埋在收件箱
13. 作为使用中文数字的用户，我希望输入"三天后"、"十五点"也能被识别，支持中文数字表达
14. 作为输入简化表达的用户，我希望"周六"能被识别为"本周六"或"下周六"（取决于今天星期几），减少输入成本
15. 作为错误输入的用户，我希望解析失败时任务仍能正常创建（标题保留原文），而不是报错或丢失数据

## Implementation Decisions

### 模块设计

**Rust 核心解析引擎**（`src-tauri/src/time_parser.rs`）
- 新建独立模块 `time_parser`，包含 `parse_time_expression` 主函数
- 返回结构 `ParsedTime { planned_start_at, due_at, title }`
- 子函数：`parse_relative_day`（相对日期）、`parse_time_of_day`（时间点）、`parse_relative_week`（相对星期）
- 使用 `chrono` 库进行日期计算，`regex` 库进行模式匹配
- 所有解析函数返回 `Option<(DateTime<Local>, &str)>`，其中 `&str` 是匹配到的原始文本片段用于从标题中移除

**前端浏览器解析**（`src/lib/quickCapture.ts`）
- 扩展 `BrowserQuickCaptureDraft` 类型，添加 `plannedStartAt?: Date` 字段
- 重写 `parseBrowserQuickCapture` 函数，支持基础的时间解析（覆盖高频场景）
- 保持轻量级，不引入额外依赖

**Domain 更新**（`src-tauri/src/domain.rs`）
- 修改 `QuickCaptureDraft` 结构，将 `scheduled_at` 拆分为 `planned_start_at` 和 `due_at`
- 更新 `parse_quick_capture` 函数，调用 `time_parser::parse_time_expression`

**Command 更新**（`src-tauri/src/lib.rs`）
- 修改 `capture_task` 命令，支持同时设置 `planned_start_at` 和 `due_at`
- 有开始时间或截止时间时，自动设置 `show_in_timeline = true`
- 系统提醒优先使用 `planned_start_at`，其次使用 `due_at`

### 解析规则

**截止时间检测**
- 触发词：包含"前"、"之前"、"截止"、"deadline" 中任一
- 示例："明天3点前提交" → `due_at = 明天15:00`，`planned_start_at = None`
- 非截止时间表达默认为开始时间

**相对日期解析优先级**
1. "N天后" / "N天後"（支持阿拉伯数字和中文数字）
2. 固定词汇：今天/明天/后天/大后天
3. 相对星期：下周一/本周五/周六
4. 如无日期表达，默认为今天

**时间点解析优先级**
1. HH:MM 格式（如 15:30）
2. 带时间段的表达：下午3点、早上9点、晚上8点
3. 单独数字+点：3点、十五点（智能判断上下午）
4. 时间段关键词：早上（9:00）、上午（10:00）、中午（12:00）、下午（14:00）、晚上（20:00）
5. 如无时间表达，默认补充 9:00

**智能判断规则**
- 单独"3点"：如果 hour ∈ [1, 7]，则 +12 视为下午；否则保持不变
- 这样"3点开会"解析为 15:00，"9点站会"解析为 9:00

**中文数字支持**
- 一、二、三、...、九、十、十一、...、二十三
- 通过 `parse_chinese_number` 函数统一转换

### 接口设计

**Rust 模块接口**
```rust
pub struct ParsedTime {
    pub planned_start_at: Option<DateTime<Local>>,
    pub due_at: Option<DateTime<Local>>,
    pub title: String,
}

pub fn parse_time_expression(input: &str, now: DateTime<Local>) -> ParsedTime
```

**前端接口**
```typescript
export interface BrowserQuickCaptureDraft {
  title: string
  plannedStartAt?: Date  // 新增
  dueDate?: Date         // 重命名自 dueDate（保持向后兼容）
}

export function parseBrowserQuickCapture(input: string, now?: Date): BrowserQuickCaptureDraft
```

### Schema 变更

`desk_tasks` 表本身无需变更，已有 `planned_start_at` 和 `due_at` 字段。但需要确保：
- `capture_task` 命令正确填充这两个字段
- 前端 `Task` 类型的 `plannedStartAt` 字段被正确使用（目前被忽略）

### 架构权衡

**为什么不用现成的 NLP 库（如 chrono-node）？**
- chrono-node 对中文支持有限，需要大量自定义规则
- 引入依赖会增加编译体积和复杂度
- 自研方案完全可控，可针对中文用户习惯优化
- 当前需求（30 个模式）用正则 + 规则完全够用

**为什么在 Rust 端而非前端实现核心逻辑？**
- Rust 的 `chrono` 库更成熟，日期计算更可靠
- 浏览器预览只是辅助，Tauri 环境才是主战场
- 前端保留轻量级解析是为了开发预览体验，不需要完整功能

**为什么要区分 `planned_start_at` 和 `due_at`？**
- 符合 GTD 理念：任务有"计划开始时间"和"必须完成时间"两个维度
- Timeline 视图需要知道何时执行任务，而非何时截止
- 提醒系统可以在开始时间和截止时间都触发通知

## Testing Decisions

### 测试原则

**只测试外部行为，不测试实现细节**
- 测试输入字符串 → 输出 `ParsedTime` 的映射关系
- 不测试内部的 `parse_relative_day` 等私有函数
- 不测试正则表达式本身，只测试端到端的解析结果

### 测试模块

**Rust 单元测试**（`src-tauri/src/time_parser.rs`）
- 测试各类时间表达式的解析结果
- 使用固定的 `now` 时间点（2026-06-14 10:00:00）避免时间相关的测试不稳定
- 覆盖边界情况：空输入、只有日期、只有时间、截止时间表达

**前端单元测试**（`src/lib/quickCapture.test.mjs`）
- 测试浏览器预览模式的解析结果
- 确保 `plannedStartAt` 和 `dueDate` 字段被正确填充

**E2E 测试**（`tests/e2e/quick-capture-parsing.test.ts`）
- 测试完整的用户流程：输入 → 解析 → 创建任务 → 显示在 Timeline
- 使用 Playwright 模拟 Quick Capture 输入
- 验证任务的时间字段在 UI 上正确显示

### 已有测试参考

参考现有的 Quick Capture 测试：
- `tests/e2e/smoke.test.ts` - 基础的创建任务流程
- `src/lib/quickCapture.ts` 中的现有解析逻辑（作为对比基准）

### 测试覆盖目标

- Rust 单元测试覆盖 20+ 时间表达式组合
- 前端单元测试覆盖 10+ 高频场景
- E2E 测试覆盖 3-5 个关键用户流程

## Out of Scope

以下功能**不在本 PRD 范围内**：

1. **绝对日期表达**：不支持"6月20号"、"下个月15号"等绝对日期（留待后续迭代）
2. **时间范围**：不支持"9-11点"、"明天全天"等时间段表达
3. **循环任务**：不支持"每周一"、"每天早上"等重复任务解析
4. **英文支持**：本版本只支持中文表达，不支持"tomorrow 3pm"等英文
5. **AI 增强**：不引入大模型进行语义理解，保持规则引擎方案
6. **自定义规则**：不支持用户自定义时间表达式映射
7. **时区处理**：只支持本地时区，不考虑跨时区场景
8. **模糊匹配**：不支持拼写纠错（如"名天"识别为"明天"）
9. **上下文记忆**：不记录用户的时间表达习惯进行个性化优化

## Further Notes

### 实施优先级

**Phase 1：核心解析引擎（必须）**
- Rust `time_parser` 模块
- 相对日期、时间点、截止时间检测
- 更新 `capture_task` 命令

**Phase 2：前端同步（必须）**
- 更新 `quickCapture.ts`
- 确保浏览器预览功能正常

**Phase 3：测试与文档（必须）**
- 单元测试 + E2E 测试
- 更新用户文档，列出支持的表达式

### 迁移计划

现有用户数据无需迁移：
- `desk_tasks` 表已有 `planned_start_at` 和 `due_at` 字段
- 旧版本创建的任务只填充了 `due_at`，新版本会正确区分两个字段
- 向后兼容：解析失败时任务仍正常创建，只是时间字段为空

### 性能考量

- 解析时间：每次 Quick Capture 提交时执行一次解析，预计耗时 <5ms
- 内存占用：解析引擎无状态，不占用额外内存
- 编译体积：新增模块预计增加 ~50KB 编译后体积（可接受）

### 后续迭代方向

完成本 PRD 后，可以考虑：
1. **绝对日期支持**："6月20号"、"下个月15号"
2. **英文支持**："tomorrow 3pm"、"next friday"
3. **AI 增强**：引入本地小模型（Qwen3B）理解更复杂的表达
4. **用户反馈学习**：收集解析失败案例，持续优化规则
