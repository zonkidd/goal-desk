# 统一持久化接缝 — 修复方案

## 问题论证

### 为什么要统一？

**当前状态**：Repository 暴露两条竞争写路径：
- **Bulk Snapshot**：`save_workspace()` + `save_desk_tasks()` — DELETE ALL + re-INSERT 全部数据
- **CRUD Traits**：`GoalRepository::update()` 等 — 单行 UPDATE/INSERT

**核心危害**：
1. **`update_goal_fields` 双写 Bug**（lib.rs L68-115）：先 `session.commit()` 全量重写所有 goals，再 `GoalRepository::update` 单行更新同一个 goal。两次写入同一实体，语义混乱
2. **全量重写的性能问题**：每次修改 1 个 task 的 status，要读写所有 tasks + 所有 activity_logs
3. **UUID 不稳定**：`save_desk_tasks` 每次用 `Uuid::new_v4()` 给 activity_log 分配新 ID，即使内容不变
4. **不可测试**：无法独立测试单个写操作，因为每个操作都依赖全量加载/保存

### 为什么选择 CRUD 路径？

**对比两种方案**：

| 维度 | 方案 A: CRUD (推荐) | 方案 B: 改进 Snapshot |
|------|---------------------|----------------------|
| 改动范围 | 中等（重写 8 个命令） | 大（重写 2 个核心函数 + diff 算法） |
| 正确性 | 高（数据库保证原子性） | 中（需手动实现 diff） |
| 性能 | 高（O(k) k=变更数） | 中（需全量加载做 diff） |
| 可测试性 | 高（每个操作独立测试） | 中（需 mock 全量状态） |
| 风险 | 低（增量迁移，每步可验证） | 高（diff 算法容易出错） |

**结论**：CRUD 路径更简单、更正确、更可测试。Snapshot 路径的唯一优势是"批量保存"语义，但 SQLite 事务已经提供原子性。

### 能否彻底解决？

**是的，4 个阶段可以彻底解决**：
- Phase 1：修复最危险的双写 bug
- Phase 2：迁移所有 Task 操作到 CRUD
- Phase 3：迁移 Goal 创建到 CRUD
- Phase 4：删除所有 snapshot 写路径

每阶段独立可部署，每阶段都有测试验证。

# 合并 Goal 进度派生 — 修复方案

## 问题论证

### 为什么要合并？

**当前状态**：存在三个独立的进度计算实现：

| 实现 | 位置 | 输入模型 | 算法 | 调用者 |
|------|------|----------|------|--------|
| Rust `goal_progress()` | domain.rs L482-514 | Todo + Milestone | 整数除法 | `goal_summaries()` → 前端 |
| Rust `Goal::compute_progress()` | domain.rs L134-145 | DeskTask | 浮点 round | 仅测试用 |
| TS `deriveGoalRecords()` | workspaceDerivation.ts L123-145 | Task | Math.round() | WorkspaceEngine → UI |

**核心危害**：
1. **双重计算**：Tauri 模式下，Rust 计算进度 → `GoalSummary.progress` → 前端 `deriveGoalRecords()` 覆盖 → 同一数据计算两次
2. **Milestone 遗留代码**：Rust `goal_progress()` 使用 Todo + Milestone，但 Milestone 已无 UI 入口（无 Tauri 命令可创建），前端也不使用
3. **潜在分歧**：如果数据库有 Milestone 数据，Rust 计算的进度分母更大，百分比偏低

### 为什么选择前端为规范？

**对比两种方案**：

| 维度 | 方案 A: 前端为规范 (推荐) | 方案 B: Rust 为规范 |
|------|--------------------------|---------------------|
| 改动范围 | 小（删除 Rust 计算 + Milestone） | 大（TS 改用 Todo+Milestone，需暴露新 API） |
| 正确性 | 高（前端直接驱动 UI） | 中（需同步 Rust 和 TS 的数据模型） |
| 性能 | 高（减少一次 Rust 计算） | 中（仍需 Rust 计算） |
| 可维护性 | 高（单一实现） | 中（两处需同步维护） |
| 风险 | 低（删除遗留代码） | 高（需修改数据流） |

**结论**：前端 `deriveGoalRecords()` 已经是实际驱动 UI 的唯一实现，Rust 计算完全是浪费。选择前端为规范最简单、最安全。

### 能否彻底解决？

**是的，3 个阶段可以彻底解决**：
- Phase 1：移除 Rust progress 计算，前端成为唯一 source of truth
- Phase 2：清理 Milestone 遗留代码
- Phase 3：移除 `Goal::compute_progress()` 遗留方法

每阶段独立可部署，每阶段都有测试验证。

# 修复浏览器 Mutation 适配器 — 修复方案

## 问题论证

### 为什么要修复？

**当前状态**：`BrowserMutations` 的 7 个 update 方法只返回 `{ statusMessage }`，不返回更新后的实体。而 `TauriMutations` 对应方法返回 `{ entity, statusMessage }`。

**核心危害**：
1. **返回值不对称**：调用者期望得到更新后的实体，但浏览器模式下得到 `undefined`
2. **Store 手动补偿**：taskStore 和 goalStore 中有 `isTauriRuntime()` 分支，手动构建更新后的对象，与适配器模式背道而驰
3. **renameArea 未被补偿**：浏览器模式下重命名领域后 UI 不更新
4. **localStorage 不更新**：刷新页面后这些更新全部丢失

### 为什么选择直接返回实体？

**对比两种方案**：

| 维度 | 方案 A: 直接返回实体 (推荐) | 方案 B: 保持现状 |
|------|---------------------------|-----------------|
| 改动范围 | 小（7 个方法 + store 简化） | 无 |
| 正确性 | 高（适配器模式正确实现） | 中（手动补偿易遗漏） |
| 可维护性 | 高（单一路径） | 低（双分支维护成本） |
| 风险 | 低（增量修改） | 中（新代码易踩坑） |

**结论**：直接返回实体是最简单、最正确的修复。

### 能否彻底解决？

**是的，2 个阶段可以彻底解决**：
- Phase 1：修复 BrowserMutations 的 7 个 update 方法
- Phase 2：简化 Store 中的 `isTauriRuntime()` 分支

每阶段独立可部署，每阶段都有测试验证。

```typescript
async updateGoalFields(goalId: string, input: { title: string; area: string; description: string }): Promise<{ goal?: GoalCard; statusMessage?: string }> {
  const title = input.title.trim()
  const area = input.area.trim()
  if (!title || !area) return {}

  const goals = loadFromLocalStorage<GoalCard>(BROWSER_STORAGE_GOALS)
  const idx = goals.findIndex(g => g.id === goalId)
  if (idx === -1) return {}

  const updatedGoal: GoalCard = {
    ...goals[idx],
    title,
    area,
    description: input.description.trim(),
  }
  goals[idx] = updatedGoal
  saveToLocalStorage(BROWSER_STORAGE_GOALS, goals)

  return { goal: updatedGoal, statusMessage: BROWSER_PREVIEW_STATUS }
}
```
